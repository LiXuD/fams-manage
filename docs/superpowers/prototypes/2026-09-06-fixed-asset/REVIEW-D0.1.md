## 3. 核心亮点（保真到位，应保留）

- **S1 数量守恒与 spec 范例逐字吻合**：phase 5（已接收 1 件）时 `count()` 返回 `[3,0,1,1,1,0]` = 申请3/待分配0/待交接1/已完成1/无法满足1/已取消0，与 §6.2 范例完全一致。
- **S2 领用链进度与 spec §8 推荐走查顺序一致**：情境选择器 ①–⑦ + "从审批开始走查(P09)"、"看盘点草图(M11)" 按钮对齐。
- **S3 evidence() 凭证区 7 字段**严格对应 §6.3/§17.3：关联资产 / 实际签收 / 发生时间 / 采集方式 / 所附依据 / 提交记录(系统) / 接收时间(系统)，且提交人与接收时间为系统记录、不由表单自填。
- **S4 独占执行与代确认的边界说明充分**：P10「关闭页面/退出/换设备不释放处理权」、P21「单管理员决定 + 当前库管执行 + 再通知生效责任人」、P22「转派不解锁资产」均落实。
- **S5 评审工具与产品界面分离清晰**：顶部明确"设计目录·非产品菜单"，画布外为评审工具，避免与产品导航混淆。
- **S6 可访问性基础到位**：`:focus-visible` 3px 描边、移动 `.phone-actions` 触控目标、状态文字化（非仅靠颜色）、`@media print` 导出样式。

## 4. 问题清单（按严重度）

### 🔴 F1 · 高 — 进度步进器 `progress()` 在 phase 2 与 phase 5 漏高亮

`progress()` 使用阈值数组 `[0,1,3,4,6]` 以「>阈值=done / ==阈值=current」判定，粒度过粗：

- **phase 2（库管处理中 / 待分配）**：step2「库管分配」既不是 done 也不是 current → 整段空白，视觉上像"审批通过后流程卡住"，与 §10.6「明确当前阶段与下一步执行人」冲突。
- **phase 5（已接收 1 件 / 部分交接）**：step4「本人接收」空白，未体现"部分接收中"。

**修复建议**（语义化阈值）：
```
提交申请   : done if phase>=1, current if phase==0
管理员决定 : done if phase>=2, current if phase==1
库管分配   : done if phase>=4, current if phase==2||3
实物交出   : done if phase>=5, current if phase==4
本人接收   : done if phase>6, current if phase==5||6
```
对应把 `state.phase>[0,1,3,4,6][i]?'done':state.phase===[0,1,3,4,6][i]?'current':''` 改为按上述区间判断。

### 🟠 F2 · 中 — 数量卡片未同时展示「待交出 / 已交出待接收」二者

§6.2 / §10.6 要求：待交接下再分「待交出」与「已交出待接收」，二者之和等于待交接量，不重复计入总量。
原型 `quantities()` 在 index 2（待交接）仅显示非零一侧小字（如「已交出 2」），缺「待交出 0」。低危但评审时应补全，否则审核员无法确认守恒口径。

**建议**：待交接卡片下固定显示 `待交出 X / 已交出待接收 Y（X+Y=待交接）`。

### 🟠 F3 · 中 — P09 并发冲突说明在「待确认」态也常驻

P09 底部 note「查看并发冲突文案」文案为"该申请已由陈琳于 14:20 批准。本次决定未保存"，但该 note 不随 `phase` 隐藏，在 phase 0（待确认）也常驻显示，与上方 banner「当前待确认」并存，易误导。

**建议**：phase===0 时隐藏该 note，或标注"（示例冲突文案，仅用于演示竞争决定）"。

### 🟠 F4 · 中 — P04 九页签多数整页跳出，未内联代表内容

spec §2.1/§10.3 把 P04 定义为"唯一资产入口 + 九页签"。当前 P04 仅「基本信息 / 当前保管 / 标签与附件」内联；其余 6 个页签（领借调拨、盘点、报修返厂、报失找回、报废、操作日志）点击即 `go()` 整页跳到 P11/P16/P17/P19/P20，草图内未展示任何代表行，"九页签"在低保真中仅为名义。

**建议**：至少「领用/借还/调拨」「操作日志」两页签内联 2–3 行代表记录（如"2026-09-06 领用申请 LY-018，待接收"），其余可保留跳转但注明"完整记录见 P1x"。

### 🟠 F5 · 中 — 离线 72h 与迟到时间裁决缺可演示交互

§8.7 / AC-25/43 的时间裁决矩阵（身份失效优先拒绝、封存后仅追加迟到、T+72h 过期）在 M12 仅以静态 banner + 回执样例文字呈现；state 无 `invSealed`/过期状态，评审无法实际触发"封存后补传""过期失效"分支，难以验证裁决顺序。

**建议**：增加 `invSealed` 开关与"封存"按钮，演示①正常接收→②封存后迟到上传（仅追加）→③T+72h 过期（安排补盘）三条路径；M11 房间可扩为 3+ 以演示多房间逐一确认。

### 🟡 F6 · 低 — P20 处置方式含"遗失核销"但未前置校验证据

下拉含「遗失核销（须遗失证据）」，草图未对"无遗失证据"做提交前拦截/提示，可能被误读为报废页可直接核销。

**建议**：选该选项时显示"须关联已确认的报失证据，否则不可提交"的拦截说明（与 §8.9 一致）。

### 🟡 F7 · 低 — 汇总数字静态且不随情境联动、未显著标注

P02（8/12/6/4）、P23（抽样 29/30）等为固定样例，不随 `phase` 变化，且未标"虚构不联动"，评审者可能误读为全局实时指标。

**建议**：在汇总卡旁加 `small`（虚构样例）或"不随情境联动"标注。

### 🟡 F8 · 低 — M11 房间仅 301/302 两值

`state.inventory` 仅 0/1 切换，无法演示"多房间逐一确认 + 换房间显式确认"完整链路。当前 2 房间足够示意，但建议注明或扩为数组。

### 🟡 F9 · 确认项 — 基础资料(P24)/系统管理(P25) 不在默认角色产品导航

spec §2.1 的 PC 导航树将「基础资料」「系统管理」列为常驻顶层；原型 `productNav` 默认角色（资产管理员+库管员）不渲染这两项，仅系统管理员角色可见，普通评审者只能经左侧"设计目录"到达。这符合 §2.3 角色隐藏，但与 §2.1 呈现略有出入。

**建议**：评审确认——是预期按角色隐藏（当前实现），还是所有角色均应在产品导航可见（仅内容/按钮按权限禁用）。若是前者，建议在目录条目标注"仅系统管理员角色可见"以免混淆。

## 6. 建议的下一步

1. **先修 F1**（高）：进度步进器是评审时判断"当前阶段/下一步由谁做"的关键元件，漏显会干扰所有走查结论。
2. **F2–F4 随视觉稿一并补**：属于"表达完整度"，不影响结构判断，但进入高保真前补齐。
3. **F5 建议补可演示分支**：离线/迟到/封存是本项目技术风险点（§8.7 复杂），草图可演示能显著降低后续开发歧义。
4. **F9 需你拍板**：导航边界属于产品决策，建议明确后同步更新 spec §2.1/§2.3 措辞。
5. 修复后建议按 spec §8 顺序重走一遍 P02→P09→P10→P11→P12→M09→M04 与 M10→M11→M12→P16→P15，确认 F1 修复后步进器与数量卡片一致。
