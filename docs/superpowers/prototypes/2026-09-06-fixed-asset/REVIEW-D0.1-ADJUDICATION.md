## 3. 关键理由与反证

### F1：不能采用审查建议的区间

审查建议把情境 1（已经批准）仍标为管理员决定中，把情境 4（已经交出）标为交出中；建议 `phase > 6` 才完成接收，而情境最大值就是 6，最终步骤永远无法结束。这会用另一套错误替换原问题。

实际场景应是：申请已提交 → 等管理员；管理员已批准 → 等库管领取/分配；分配已结束 → 等交出；实物已交出 → 等接收。情境 5 明确待接收 1 件；情境 6 无待处理量，处理阶段结束但申请结果是部分完成，不能把“步骤结束”解释成申请3件全部领到。

D0.2 在非终态恰有一个当前步骤，终态没有当前步骤；数量和结果继续独立显示。该映射限定在本原型的七个示例情境，后续系统应以真实明细状态聚合。

### F3/F4：区分打开示例、切换页签与跳转原单

修改前浏览器证据：P04 点击“领用 / 借还 / 调拨”后仍停留 `index.html#P04`，正文包含两条内联时间线，“查看原始记录”需要另点才跳转。P09 冲突文字也在点击示例按钮后才进入弹窗，不是待确认正文常驻结果。因此审查中的行为事实不能照收。

但原时间线在不同业务页签重复，操作日志缺操作者与结果；通用原单入口还会打开另一资产的维修等示例。真实资产查询需要确认“这是这件实物的记录”。本轮补足有业务意义的内联内容，并为没有相关历史的资产显示空态。

### F5：应该演示裁决结果，不赋予错误角色能力

普通员工不能在盘点现场点“封存任务”。管理员封存仍在 P15；画布外情境切换只用于展示任务已封存的客观事实。M11 一旦已知封存，停止原任务采集；M12 对旧证据按以下顺序示意：

1. 账号、绑定失效优先拒绝；即使有旧回执也不恢复访问，界面不继续显示资产证据。
2. 身份有效且已有同一事件回执，超过截止时间仍返回原结果，不重复计数。
3. 首次上传时间异常不自动采信；首次上传达到72小时则过期，不当成迟到证据。
4. 有效、未过期但任务已封存，只追加迟到证据，原报告与完成数不动。
5. 正常可接受证据只计一次；旧分配记录只供复核，不能自动计入。

加入这些局部情境足以评审“用户将看到什么、下一步做什么”。未建设真实离线缓存、版本校验、服务端时间校准或微信接口，不能据此声称通过 PRD 的真实离线验收。

### F8：关联发现比第三房间更值得修

复核现场切换时发现，原 M11 的账面位置和实盘房间使用同一个变量；切到301时账面也变为301，导致位置差异被隐藏。这违背 PRD §8.7 的固定任务快照原则，直接影响现场判断。

现固定账面302，实际房间可在302/301显式切换。在301识别该资产时，显示账面302与实际301，并提供“保存位置差异”，不能继续声称与现场一致。无需增加房间数量。

### F9：目录全集不等于每人菜单全集

系统管理员可维护身份和角色，但没有自动业务权；反过来，资产管理员兼库管也没有自动系统配置权。原型按页面视角给出角色示例，画布外目录允许评审者查看全部角色页面，不是给当前员工赋权。保留现有隐藏方式并明确这一区分，无需用户再次决定已由 PRD 确定的边界。

## 4. 验证与未覆盖范围

验证结果与截图统一记录在 [原型说明与走查](README.md)。验证对象是 D0.2 页面内容、原型状态反馈和导航，不是服务端业务、真实并发、微信能力或生产离线安全。PRD 的53项AC仍为后续实现验收目标；设计覆盖映射不等于53项全部测试通过。
