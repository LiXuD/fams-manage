## 必须冻结的设计决策

1. 内部数据库主键优先采用 MySQL signed `BIGINT AUTO_INCREMENT`，API 统一使用十进制字符串；资产编码是全企业唯一、永久不复用的独立业务标识。
2. 业务事件时刻使用 Java `Instant`、API UTC `Z`、MySQL UTC `DATETIME(3)`；业务日期使用 `LocalDate` / `DATE`，服务端当前时间来自可注入 `Clock`。
3. 二维码使用不可猜测的随机访问标识；重打保持同一标识，明确换标才轮换并使旧标识失效；扫码只定位授权检查入口，不授予业务权限。
4. PC 使用安全 Cookie 会话和 CSRF 防护；系统账号、初始密码修改、失败锁定、停用和角色变更的失效语义在契约中可观察。
5. 管理员决定与库管处理权分离：任意一名资产管理员只能产生一个有效决定，批准后由首个合法库管原子取得整单唯一处理权；当前处理库管才能验收入库。
6. Flyway 产品迁移位置与 D6-02B 技术探针位置隔离；迁移只前向追加，失败不得编辑已执行脚本，恢复设计不得依赖 down migration。

以上为本计划既有规则的任务落地，不新增多租户、多级审批、BPMN、采购、财务或通用工作流。

## 正向、拒绝及恢复路径

- **认证：** 正确登录、首次改密、当前会话读取和注销；错误密码、锁定、停用、旧会话、缺失/错误 CSRF 分别返回固定错误。
- **基础资料：** 分页读取、创建、修改和停用；重复编码、循环组织/位置、停用引用、停用位置仍有资产、越权或过期版本必须拒绝。
- **建卡：** 保存允许缺少非关键字段的草稿、补全并提交入库、复制时排除编码/序列号/状态/责任、列表/详情及标签重打；重复编码/序列号、停用主数据、不完整提交、直接改状态/责任必须拒绝。
- **入库：** 创建/修改草稿、提交并取得资产锁、单管理员竞争决定、库管竞争认领、当前处理人验收；旧版本、重复决定、他人写入、仓库位置失效、部分写入及响应丢失重试必须有明确结果。
- **恢复：** 设计说明迁移启动失败、事务失败、响应未知和应用重启后的恢复入口；只描述后续实现必须验证的机制，不将文档审查冒充运行结果。
