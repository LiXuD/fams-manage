# D6-11A 领用事实表契约

2026-10-07。迁移：`V19__create_requisition_facts.sql`。依据 PRD V1.5 §7.2、§8.4。
这是持久化契约；HTTP 操作、页面与业务授权由 D6-11B/C 实现。

| 表 | 事实和不变量 |
|---|---|
| `fams_requisition` | 编号唯一、创建人、业务状态、请求内容版本与乐观写版本、参数快照、后续来源及原因快照。请求版本只在需求内容变化时前进，执行升版不改变批准的需求版本 |
| `fams_requisition_demand` | 类别/规格/偏好/用途/期望日/目标快照与数量。个人只指定实际使用人，公用只指定部门责任人；组织和位置均必填。五个互斥结果桶非负且合计等于申请数量 |
| `fams_requisition_decision` | 每个请求内容版本只存在一个决定，保存完整批准范围 JSON、决定人、时间、原因与关联审计。服务不得覆盖已有决定，重新申请按新版本再次审批 |
| `fams_requisition_ownership` | 单据最多一条未归档整单处理权；归档旧处理权保留历史。处理权与资产分配通过同单据复合外键关联 |
| `fams_requisition_allocation` | 每个具体资产分配关联需求、处理权、全局资产锁和审计，保留资产快照及前次分配。待交出/交出待接收/收回待取消禁止重复活动分配；已取消/已接收保留历史，允许未来正式业务合法再次使用 |
| `fams_requisition_unfulfillable` | 每次按正数量记录受控原因、申请要求、执行人/时间、库存查询结果摘要和审计；OTHER 必须填写说明 |
| `fams_requisition_followup` | 每条来源需求只有一个最新后续指针；复合外键同时核对来源申请、来源需求和最新申请上的来源，拒绝跨单引用、普通申请冒充后续和指向自身 |

## 数量与状态

申请数量 = 待分配 + 待交接 + 已完成 + 无法满足 + 已取消。
已分配总量只由待交接 + 已完成计算，不另存可漂移字段。

草稿提交不锁库存；批准表示允许履行。未认领为 `WAITING_WAREHOUSE_CLAIM`；
认领后待交接优先于待分配。有已完成量但仍有待分配时继续 `WAREHOUSE_PROCESSING`。
无待处理量后才按全完成、部分完成、全取消、零履行且无法满足确定终态。
上述单头投影必须由 B/C 的事务实现并检验，A 的表约束本身不证明状态机已实现。

## 后续服务必须承担的检查

- 当前账号/人员、角色/授权版本、PC 或小程序凭证、目标组织/人员/位置的活动状态和范围；不能只使用请求开始时快照。
- 已批准需求内容不可随执行修改；批准范围内替换未交出资产应保留旧分配及取消原因。
- 全局 `fams_asset_business_lock` 为跨业务唯一锁。分配必须锁定资产并核对在库、正常、版本、类别和当前无锁，再原子写锁/分配/数量/审计/待办。
- 分配中的 `business_lock_id` 外键只证明锁存在；资产、单据及需求是否与锁一致仍须在事务中重验。
- 无法满足记录累计量与需求结果桶必须同事务前进；不能仅插入原因事实而漏改数量。
- 同一来源指针在行锁下创建或返回最新草稿。再次允许条件、来源无法满足量上限与最新链履行情况由服务检查，唯一约束不能替代这些业务判定。
- 已接收量永久保留；后续退库/归还/报失另开业务，不能改小历史已完成量。
- 申请人异议复用既有站内待办，在原申请上去重，不新加审批层。

## 迁移和恢复边界

V19 只增加表和新表间外键，不改 V1～V18 的已发布字节、不搬迁既有数据。
MySQL DDL 不承诺整份脚本原子回滚；失败时先核对 Flyway 历史与真实对象，不能直接
`repair` 把部分表认成成功。任务自有库可清理重建并复跑；共享/生产库需在部署前备份，
依据实际失败位置制定前向修复，不降版或删除已写入领用事实。

本轮使用独有随机 MySQL 8.4.11 库验证空库、V18 升级、无重复迁移、既有组织版本/名称
保留、CHECK/FK/唯一约束、同一事务失败回滚和双连接并发处理权竞争。
这不证明领用 API、真实页面、进程崩溃恢复、共享/生产升级或备份恢复已经通过。
