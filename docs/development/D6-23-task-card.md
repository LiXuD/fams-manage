# D6-23 全状态期初承接任务卡

执行依据为 PRD V1.5 §16.5（期初导入窗口）、§7.5（报废状态流转）与 AC-30/31，页面按 IA D0.2 的 P18（期初导入）与 P20/M07（报废）接续。状态明细维护在第六阶段开发计划 §四.5 的 D6-23A/B/C。以下前段记录 A 的首轮交付，第三批联合结果见本文末尾。

## 业务结果

上线前的待报废实物在初始化窗口内随批次一次发布：资产卡直接进入待报废并冻结原保管关系，系统在同一发布事务里建立一张待管理员确认的期初报废申请、一条活动报废锁和一条管理员审批待办。发布不等于批准报废——报废事实来自上线前既有记录，是否批准处置范围仍由任意一名管理员单独决定。申请不伪造员工提交，也不复用报失或维修来源。

批准后的办理与独立报废完全同源：共享池首位库管认领取得唯一处理权，实物核验按批准范围执行后进入已报废并建立待处置事实与处置待办。驳回按记录的报废前快照恢复原保管关系并释放本单锁，责任与异常状态不被清除；作废沿用同一快照口径。整批回滚只在这张期初申请仍未办理时允许，回滚把申请转已取消、释放锁、关闭待办并逐字段保留事实。

## 数据与契约

V64 为 `fams_scrap_request` 增加 `initial_batch_id` 与 `initial_sheet_row`：批次外键、`(批次, 原行号)` 唯一键，以及检查约束——要么两者为空，要么同时非空、行号不小于 2 且不携带业务来源标识。既有报废单据的两列为空，升级不回填、不改写任何历史行。

预检把资产状态扩展为 `在库/在用个人/在用公用/借出/待报废`。`待报废` 行必须给出报废前状态，且只能是 `在库/在用个人/在用公用` 之一，并按该状态校验完整保管快照（仓库与仓位，或使用组织、使用人及当前位置），另须填写报废原因、报废前现状与建议处置方式，长度分别不超过 2000/2000/500。遗失、维修中和返厂维修来源的期初行继续被拒绝，对应承接随后续切片开放。

发布写入的申请保存与正常提交同构的资产快照列集（含报废前生命周期），因此驳回与作废沿用既有恢复校验；`source_type` 保持 `STANDALONE`，来源批次与原行号写入新列并在详情响应 `initialSource` 中回显。

## 双端接入

PC 报废详情为期初承接单显示批次与原行号，并提示批准仍需管理员另行决定；小程序原生报废详情同口径。PC 期初导入的模板与列映射新增报废前状态、报废原因、报废前现状、建议处置方式四列，模板说明页写明待报废的填写要求与不批准口径。

## 已交付与验证

- V64 有数据升级：在原库先升到 V63 并写入一张已执行报废单，升级后该行 19 个既有列逐字段不变、两个新列为空；重复迁移 0 项执行；新列受唯一键约束（同批次同行号重复登记被拒），部分为空或行号小于 2 被检查约束拒绝（错误码 3819），未知批次被外键拒绝（错误码 1452）。
- 期初导入真实 HTTP/MySQL 全链路：两行待报废（在库与在用个人）发布后，原机为 `PENDING_SCRAP`、版本 0、保管类型分别为 STORAGE/PERSONAL，各带一张 `PENDING_ADMIN_DECISION` 申请、一条未释放报废锁、一条 ASSET_ADMIN 池的审批待办和一条 `SCRAP_INITIAL_OPENED` 事件，快照记录报废前生命周期与批次行号且无处置回执。批准→认领→实物执行按批准范围转 `SCRAPPED` 并建立 `PENDING_DISPOSITION`，原锁释放、审批与认领待办关闭并新产生处置待办；批准之后整批回滚返回 409。在用个人行被驳回后原机回到 `IN_USE`/PERSONAL、保留原使用人与组织、异常仍为正常、版本 0→1，锁以 `SCRAP_REJECTED` 释放且无遗留待办。未办理的批次可整批回滚：申请转 `CANCELLED`、版本 0→1、锁以 `SCRAP_INITIAL_ROLLED_BACK` 释放、待办关闭并记 `SCRAP_INITIAL_ROLLED_BACK` 事件，原机卡转 `CANCELLED` 且保管字段清空。报废前状态填 `借出`、缺报废原因、状态填 `维修中` 三类行分别按 `UNSUPPORTED_PRE_SCRAP_STATE`、`REQUIRED`、`UNSUPPORTED_INITIAL_STATE` 报告且不发布。
- 回归：V59～V63 五个升级用例在同一数据库复跑各 1 项通过；持久任务、导入批次与期初导入 HTTP 套件通过；报废提交 11 项、报失 HTTP 44 项、维修 HTTP 18 项通过；架构 6 项、契约 9 项、预检单测 14 项通过；Web 236 项（新增期初承接详情用例）、小程序 339 项通过；Checkstyle 与 SpotBugs 零报告，类型、lint 及双端构建零问题。原始日志见 output/d6-23-initial-scrap-runtime.log。

## 验证中发现并修复

- 期初申请的 INSERT 占位符与列序错位，导致 `source_type` 收到快照 JSON 而报数据过长；发布事务整笔回滚。修正字面量位置后通过。
- 整批回滚的下游守卫把本批次自建的期初报废锁计为外部业务，使待报废批次永远无法回滚。守卫改为只拒绝非本批期初申请的锁，回滚可达性仍由申请未办理断言保证。
- 报废执行的实际核验时间改用毫秒截断（与既有报废套件一致），否则带微秒的机器时钟会触发 `SCRAP_PHYSICAL_EVIDENCE_INVALID`。
